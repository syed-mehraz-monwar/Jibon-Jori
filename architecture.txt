JibonJori – Architecture & Implementation Plan

Status: Architecture approved. Database/ERD approved. Prisma implementation is the next stage.
Important: This document describes the approved architecture and implementation direction. Do not change architectural decisions without explicit approval.

0. Project Overview

JibonJori – AI Assisted Matrimony Platform is a modern web-based matrimonial platform where users can:

Create verified matrimonial profiles
Manage personal information and partner preferences
Search and filter potential partners
Receive AI-assisted compatibility scores and recommendations
Like, dislike, favorite, rate, and comment on profiles
Receive real-time notifications
Use an AI chatbot for profile and matchmaking assistance
Upload profile photos/documents
View location information using Google Maps
View curated YouTube content
Generate reports from real application data
Use secure authentication with email/phone OTP
Maintain revocable server-side sessions

The project is designed as a containerized modular monolith, not a microservice architecture.

18. Media & Firebase Storage

Actual uploaded files are stored in Firebase Storage.

The media model stores information such as:

19. Interactions

Likes, dislikes, and favorites use one unified table:

interactions

Values:

-1 = dislike
 1 = like
 2 = favorite

A user/profile has one current stance toward another profile.

The primary key is:

(actor_profile_id, target_profile_id)

A favorite may imply a like at the application level.

Unlike should remove the interaction or otherwise update the stance according to the approved service behavior.

Users cannot interact with themselves.

20. Ratings

Profiles can receive ratings from other profiles.

Rating:

1–5

A profile can rate another profile only once at a time.

Rating averages should be calculated from source ratings.

Do not store unnecessary derived aggregate values in the database unless explicitly approved.

21. Comments

MVP comments are intentionally flat.

There is no parent_id in the MVP.

Comments contain:

Threaded comments may be introduced later if required.

22. Compatibility System

Compatibility scores are stored in:

compatibility_scores

The table is a current, recalculable cache, not an immutable historical record.

The MVP does not store personality scores.

Initial compatibility factors may include:

overall score
interests score
education score
profession score
location score
preference score

Scores are stored with:

model version
inputs hash
computation timestamp
23. Compatibility Pair Canonicalization

Compatibility between two profiles is unordered.

Therefore:

Profile A + Profile B

and:

Profile B + Profile A

must refer to the same database row.

The system must canonicalize the pair:

smaller UUID → profile_a_id
larger UUID  → profile_b_id

The application service must enforce this consistently.

A database-level constraint should also be used where PostgreSQL/Prisma implementation allows it.

24. Compatibility Recalculation

Compatibility should not be precomputed for every possible pair.

The system should calculate compatibility on demand and/or through controlled recommendation jobs.

Use:

inputs_hash

to determine whether the underlying inputs have changed.

If inputs have not changed, the cached result can be reused.

If inputs change, the compatibility score can be recalculated.

This prevents unnecessary N² computation.

28. PostgreSQL Extensions and Raw SQL

Prisma cannot express every PostgreSQL-specific feature required by the approved design.

The implementation must identify and handle features such as:

pgcrypto for UUID generation where required
citext
partial unique indexes
partial indexes
advanced CHECK constraints
canonical compatibility pair constraint
any other PostgreSQL-specific constraints Prisma cannot represent directly

These must be implemented through documented supplementary raw SQL migrations where necessary.

Do not silently remove database-level constraints simply because Prisma cannot represent them.
